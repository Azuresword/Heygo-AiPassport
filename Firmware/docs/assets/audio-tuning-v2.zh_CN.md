# Heygo 音频调优 V2

## 目的与证据

V2 针对播放中的短暂停顿和声音突然开始。它保持 V1 的输出音量 `90`，并保留电平计数器。
音频格式仍为 16 kHz、16 位、单声道，通过 BLE 传输 IMA ADPCM。

基线日志包含以下独立样本：

| 样本 | 记录值 |
| --- | --- |
| 一次回答 | 248 块，4.96 秒，缺失 0 块，峰值 28927，接近满幅的样本 0 个 |
| 该回答的播放 | 欠载 4 次，丢弃 0 块，无效 0 块 |
| 一次录音 | 312 块，峰值绝对值 32768，接近满幅的样本 178 个 |

`underruns` 计数器记录应用队列为空时尝试写入的静音块数。它不测量硬件 DMA 欠载。
电平计数器测量 PCM 样本。它们不测量喇叭输出。
接近满幅的阈值是样本绝对值 32700。有符号 16 位样本 −32768 的绝对值为 32768。
这些样本支持分别检查播放时序和录音削波。它们不能确定可闻失真的原因。

## 本版选择

1. 仅在成功完成三次 20 ms BSP 写入后，启用 20 ms 宽限期。
2. 在 `WAIT` 期间，请求的任务轮询延时不超过 5 ms。
3. 数据块到达后恢复播放。播放开始后，不再等待三块数据。
4. 先检查现有的流结束规则和 2 秒停滞规则，再进入宽限等待。
5. 在第一个有效块的前 64 个样本内线性淡入，即 4 ms。
6. 插入静音或遇到无效数据后，再次应用淡入。普通 `WAIT` 后不应用淡入。

启用后，每次队列变空均获得一次宽限期，再插入静音。成功写入音频或零值均计入这项保护条件。
从队列取出或丢弃数据块不计入。写入失败也不计入。
成功写入不足三次时，播放中遇到空队列仍立即写入静音，与原行为一致。
收到 `PLAY_END` 后，空流仍立即结束。这项保护不在 `PLAY_END` 后补齐数据。

启动时，一次或两次写入可能留下未填满的 DMA 描述符。继续等待 20 ms 可能使其中的数据未获使用。
三次写入提供 960 帧，可填满当前四个描述符，每个描述符包含 240 帧。
这为宽限期提供余量。BSP DMA 配置变化后，必须重新检查这项保护条件。

初始缓冲规则保持不变：累计三块、首块到达后经过 60 ms，或收到 `PLAY_END`，均可开始播放。
三次写入保护、20 ms、5 ms 和 64 个样本是本项目的设计选择。下列资料没有规定这些参数。
请求的轮询延时不保证任务调度延迟。

V2 保留现有的播放汇总，便于对比。它增加 `playback feed` 汇总：

| 字段 | 含义 |
| --- | --- |
| 供数时长 | 从进入 `play_loop` 到输出汇总的经过时间 |
| 首次静音 | 从进入 `play_loop` 到首次尝试写入静音的时间，没有则为 `-1` |
| 最长写入时间 | 音频写入调用的最长实测耗时 |
| 写入错误 | 音频写入错误的次数 |
| 淡入次数 | 应用淡入的次数 |

这些时间测量软件调用。它们不测量 DMA 完成时间或喇叭实际出声时间。

## 研究依据与范围

以下官方资料的检索日期为 2026-10-17。

| 资料 | 资料中的原理 | 本项目选择 |
| --- | --- | --- |
| [ESP-IDF 5.5.3 I2S](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32c3/api-reference/peripherals/i2s.html) | I2S 写入将 PCM 复制到 DMA 缓冲。缓冲空间不足时等待。返回不代表声音已播放完。 | 使用现有的阻塞音频写入。每次写入后不再增加固定的 20 ms 延时。 |
| [WebRTC NetEq Expand](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_coding/neteq/expand.cc) | 丢包处理使用衰减窗、重叠相加和淡入淡出。 | 在静音之后短暂淡入。这不是 NetEq 算法，也不是完整的丢包隐藏。 |
| [WebRTC GainController2](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/gain_controller2.cc) 和[自适应增益控制](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/agc2/adaptive_digital_gain_controller.cc) | 先增益，后限幅。自适应增益还考虑峰值余量、噪声和增益变化限制。 | 检查现有峰值前，不增加自动增益控制，也不继续放大。 |
| [WebRTC 高通滤波器](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/high_pass_filter.cc) | 滤波系数取决于采样率。 | 没有频率测量结果时，不增加均衡处理。 |
| [Speex 手册](https://www.speex.org/docs/manual/speex-manual/node7.html) | 预处理器提供增益控制和降噪。它支持按音频帧处理。 | 本次时序调整不增加新的处理库。 |

V2 不增加自动增益控制、均衡处理或外部库。它不提高 V1 的输出音量。
V2 不实现淡出。它不修复录音削波、物理功放失真或所有 DMA 欠载。
20 ms 宽限期可能耗尽 DMA 中剩余的音频。实机测量必须检查这个取舍。

## 验证与后续调优

主机检查必须覆盖成功写入一次或两次、第三次成功写入、零值写入，以及不计入的写入失败或丢弃块。
还必须覆盖宽限期到期、宽限期内到包、立即结束且不补齐数据、停滞到期和计时器回绕。
淡入检查必须覆盖有符号极值、首个有效块、静音恢复、无效数据和普通等待。

实机 A/B 对比按以下顺序执行：

1. 在 V1 和 V2 上播放同一段干净语音。
2. 保持设备位置、收听距离、输出音量和电池条件可比。
3. 记录应用欠载、缺失块、丢弃块、无效块和输入峰值。
4. 比较起始爆音、停顿、语音清晰度和播放结束行为。
5. 使用自然语音和人为 BLE 延迟重复测试。
6. 修改麦克风增益前，先检查录音 WAV。
7. 增加均衡处理或继续提高输出增益前，先测量喇叭响应和失真。

如果录音持续削波，单独测试麦克风增益。如果干净的 PCM 仍有失真，比较较低输出音量，并检查功放通路。
分别记录每次改动及结果。不能仅凭构建成功或应用计数下降，判断声音已经改善。
